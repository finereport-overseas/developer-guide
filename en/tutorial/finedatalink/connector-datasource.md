# Connector Data Source Fetch Interface

| Property | Value |
| --- | --- |
| Interface Type | provider (data source connector) |
| Module | `extra-fdl` |
| Product | FineDataLink (FDL) |

## Overview

Starting from FDL 4.1, the **data source connector fetch plugin interface** is open for extension. It lets you extend the input source of *Data Sync* and the input operator of *Data Transform*, so data can be read from various source systems.

Fetching data is done through three cooperating interfaces:

1. **Operator interface (InputNode)** — defines the type and structure of the input operator, holding the properties configured by the user on the panel.
2. **Data connection interface (Connection)** — defines the basic configuration and creation of a data connection (optional; e.g. an API may skip it).
3. **Connector data source interface (Datasource)** — defines the data type in FDL and produces the result set from the operator's configuration.

## Plugin Openness Principles

- Parameters and return values of interface methods should avoid directly depending on classes from the main jar.
- Plugins should not directly implement the data-structure interfaces of the main jar; use a proxy to shield against interface changes.
- All externally exposed types are annotated with `@Open`.
- Expose as few interfaces as possible; open more incrementally based on demand.

## Three Components of a Connector

### 1. Operator Interface (InputNode)

The operator type's configuration is customized by the developer and stored in the operator node.

- **Type**: implement `InputNodeTypeProvider` (which declares the `XML_TAG` constant). The plugin interface is proxied by `PluginInputNodeType`. Once injected in `plugin.xml`, `DataFlowNodeTypes` can discover this type.
- **Structure**: `PluginInputNode` extends the input operator abstract class `AbstractInputNode`, reusing the common properties and methods of input operators. It holds a reference to `InputNodeProvider` — an interface you implement. All your custom properties live in `InputNodeProvider`, so its implementation must support Jackson deserialization; the concrete class is resolved by a custom deserializer that picks the class based on the operator type.

Sample code for the framework to discover operator types:

```java
Set<InputNodeTypeProvider<InputNodeProvider>> array =
        ExtraFdlClassManager.getInstance().getArray(InputNodeTypeProvider.XML_TAG);
Map<String, PluginInputNodeType> pluginProviders = array.stream()
        .collect(Collectors.toMap(InputNodeTypeProvider::id, PluginInputNodeType::new));
pluginProviders.forEach(allDataFlowTypes::putIfAbsent);
```

### 2. Data Connection Interface (Connection)

- Implementation references the FR data-connection plugin interface. The difference is that the connection configuration must implement `PluginNRdbmsConnectionConf`, which ultimately extends FR's `AbstractDatabaseConnection`.
- You must additionally implement the interface that returns the data source type name; it must match the FDL data source type.
- Injection: front-end panel injection + back-end interface injection (refer to the FR plugin's data-connection implementation).

> The data connection is **optional**. Sources without a common configuration (e.g. API) can skip it and configure everything directly in the operator.

Overall flow:

1. Define the data connection configuration (optional).
2. Select a specific data connection in the operator (optional).
3. Configure other properties in the operator.
4. The data source interface produces the result set from the configuration generated by the operator.

### 3. Connector Data Source Interface (Datasource)

- Similar in idea to the JDBC data source interface, but fewer interfaces need to be implemented (beyond the data source name and license validation).
- The key method creates the `ResultSet` from the configuration: `AbstractNRdbmsResultSetProvider createResultSetProvider(Map<String, Object> conf)`. The `conf` argument is generated by the operator's configuration class.
- `AbstractNRdbmsResultSetProvider` is designed after the JDBC `ResultSet`. Its four key methods are:

| Method | Description |
| --- | --- |
| `next()` | Whether another row exists; if so, move the cursor down one row |
| `getRow()` | Get the current row of data |
| `currentCurs()` | Get the current row index; starts at -1, becomes 0 after `next()` returns data |
| `getMetaColumns()` | Get the collection of column types |

Sample code for the framework to discover data sources:

```java
Set<NRdbmsDatasourceProvider> nRdbmsDatasourceProviders =
        ExtraFdlClassManager.getInstance().getArray(NRdbmsDatasourceProvider.XML_TAG);
nRdbmsDatasourceProviders.forEach(datasourceProvider ->
        result.put(datasourceProvider.dsType(), new PluginNRdbmsDatasource(datasourceProvider)));
```

## plugin.xml Registration

Like other FDL extension points, register the implementation classes under the `extra-fdl` tag:

```xml
<extra-fdl>
    <InputNodeTypeProvider class="com.fr.plugin.fdl.xxx.YourInputNodeType"/>
    <NRdbmsDatasourceProvider class="com.fr.plugin.fdl.xxx.YourDatasourceProvider"/>
</extra-fdl>
```

- The data connection configuration (if any) is also declared under `extra-fdl`.
- Sources without a common configuration (e.g. API) can skip the connection and configure only in the operator.

## Plugin Development

- The front-end panel configuration must correspond to the fields of the operator/connection configuration classes and support deserialization.
- Full frontend guide: [Connector Data Source Read Plugin Interface (Frontend)](./connector-datasource-frontend.md)
- Full backend guide: [Connector Data Source Read Plugin Interface (Backend)](./connector-datasource-backend.md)

## Notes

- User-defined configuration classes (e.g. `InputNodeProvider` subclasses, connection configuration classes) must support Jackson deserialization, with fields matching the front-end form items.
- The data connection is optional; whether to provide one depends on whether the data source has a common connection configuration.
- Interfaces evolve with FDL versions; exact method signatures and package paths follow the actual `fdl-plugin-interface` API.
